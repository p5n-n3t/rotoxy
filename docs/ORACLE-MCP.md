# OAuth-isolated Oracle MCP tools

`src/oracle-tools.ts` exports the four `oracle_*` MCP definitions, `isOracleToolName`, `oracleToolRequiredScope`, and `OracleTools`. Gateway wiring should expose `oracle_submit` to clients with `jobs:write` and the catalog/status/result reads with `jobs:read`; pass the authenticated OAuth `client_id` to every `call(name, args, clientId)` invocation. The tool layer hashes that client ID into a stable internal task-ID prefix, then appends the caller's validated `jobId`. Every status and result response is checked against that exact internal ID, so clients cannot address another caller's queue row by choosing an ID.

`oracle_submit` accepts a caller job ID, prompt of at most 4,000 Unicode characters, and an optional model limited to `qwen3.5:9b`, `gpt-oss:20b`, or `tev1:0.8b`. It sends the prompt only through child-process stdin to `/usr/bin/python3 -m snooze.oracle_pool ... submit --stdin`. The Python command durably queues the text and returns; it does not invoke inference. A separate local Oracle worker (`snooze.oracle_pool serve`) must consume queued work later. Reusing the same client and job ID retries idempotently; Python rejects changed prompt/model content for an already-used task ID.

`oracle_catalog` reads the cached local host/model catalog only; it never adds `--refresh`, exposes no host IPs or global assigned-task counts, and filters models to the allowlist. `oracle_status` returns bounded state, host ID, actual/requested model, attempts, token counts, and timing. `oracle_result` includes text only after completion and enforces the queue's 16 KiB UTF-8 result bound. Neither tool lists tasks globally or returns submitted prompts. Pool command failures and stderr are discarded or mapped to short safe error codes.

The command and all arguments are fixed by the module; no shell is used and callers cannot select an executable, subcommand, config path, or database path per request. The constructor accepts explicit `supervisorCwd`, `configPath`, and `dbPath` for gateway wiring and tests. Defaults point to the package's `supervisor/` directory and the private `~/.local/state/token2oauth/oracle-pool/{config.json,queue.sqlite3}` state paths. No provider credentials are stored by this tool layer. The Python pool is responsible for keeping those local files private.

Command execution is bounded by timeout and stdout bytes, with stderr discarded. Prompt text is bounded before launch and never placed in argv. Closed-key argument validation runs before invoking Python. The gateway's OAuth authorization remains responsible for deciding which tools a client can see and call; the client hash provides per-job data isolation inside the shared local Oracle queue.

Tests exercise the injected command runner for fixed argv, stdin-only prompts, idempotent caller namespace, strict input validation, bounded outputs/timeouts, and safe errors. When `/usr/bin/python3` is available, a temporary private SQLite/config integration test submits and polls a queued job without starting the inference worker or making SSH calls. This module is not yet wired into the gateway by itself; root integration must connect the exported definitions, scope helper, and class.

Enable the gateway facade with `token2oauth serve --oracle-pool`. The existing private pool config and queue must be configured separately. `jobs:read` authorizes catalog/status/results; `jobs:write` authorizes submission. Without this flag, Oracle tools are not advertised or executed.
