# Oracle pool maintenance fence

The queue stores a durable `pool_maintenance` singleton beside tasks. Initial epoch zero is created only when the table itself is first migrated, under the same serialized schema transaction. An existing table with a missing or invalid singleton fails closed on restart. Epoch/revision compare-and-swap requests pause claims; only the daemon claim transaction acknowledges after running, ambiguous, dispatching, and unknown-status blockers drain. Queued work remains queued. Release is an explicit epoch and revision CAS that resumes claims without restarting the pool or changing configuration. The fence never expires automatically.

`OraclePool.open_maintenance(db_path)` constructs a controller for validated existing state only: it does not load or create config, initialize schema, or recover stale claims, and all connections use SQLite `mode=rw` so a missing file is never created. `read_maintenance_status(db_path)` provides a stable six-key DTO on a read-only connection and never initializes or acknowledges. Both reject missing/corrupt state. Release callers pass `expected_epoch=` and `config_revision=` explicitly.

The maintenance CLI commands use the existing-state-only controller. Validation uses temporary SQLite databases and fake transports; no Oracle host was contacted. The root admin can use the read-only helper for status and the factory for explicit request/release. A future admin must not claim acknowledgement until the daemon has observed the drained fence.
