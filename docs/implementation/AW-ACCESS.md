# Agent Workspace access editor

OAuth clients do not receive Agent Workspace membership when they register. `SupervisorRuntime.workspaceProjects(clientId)` exposes only project IDs already present in that client's explicit `clientIds` bindings, and normal `authorizeWorkspace` checks the live in-memory config on each call.

The authenticated `/admin/agents/access` router lets an administrator select a configured project and registered, non-revoked OAuth clients. Updates change only that project's `clientIds`, validate the candidate with the existing strict runtime-config parser, and atomically replace the owner-only config after writing a mode-0600 `.bak`. An exclusive sidecar lock plus an opaque SHA-256 revision rejects stale/concurrent edits. New client IDs, unknown projects, caller-provided paths, and arbitrary config fields are not accepted. A runtime without a persisted config path exposes read-only membership and rejects writes. An empty client list is valid and revokes access for every client on that project.

Integration is complete in the current source: `server.ts` mounts `createAgentWorkspaceAccessRouter(store, sessions, supervisorBackend)`, and the Agent Workspace page links to `/admin/agents/access` as “Client access.” The authenticated MCP `workspace_projects` tool calls `AgentWorkspaceService.authorizedProjects` with the verified OAuth client ID; the supervisor returns only projects whose explicit `clientIds` binding includes that client, then rechecks each project with `authorizeWorkspace`. The tool accepts no project or client ID from its arguments. Do not infer membership from client registration or user-supplied project IDs. The admin route uses the shared admin session and CSRF token, requires a matching `Origin`, and sets `Referrer-Policy: same-origin` so form submissions retain a same-origin Origin header.

Validation uses isolated temporary configs and stores; no OAuth credentials, provider calls, or live runtime config are required. The current source includes the server mount, page navigation link, and client-scoped MCP discovery tool.

## 2026-10-21 — Optional shared ROTOXY workspace

The original explicit project-binding behavior described above remains the default. A new **opt-in**, owner-private sharedWorkspace supervisor policy permits a consented OAuth client to access one designated central provider workspace without being added to every folder-project clientIds list. Consent is established only by an unexpired issued gateway refresh grant with the MCP scope; dynamic registration alone is insufficient. The access token must still pass regular issuer, audience and method scope checks. Unrelated projects retain the exact explicit project grants described above. Runtime authorization re-reads the private config so external changes become effective without service restart. See docs/architecture/shared-workspace-access.md for the precise policy and endpoint distinctions.
