# Agent Workspace reconciler — 2026-10-16

The reconciler is wired into `startServer`, not `buildApp`. When a supervisor backend/runtime is configured, `AgentWorkspaceService.createReconciler()` starts it with the server; the server's `close` handler stops it. It has no timer when constructed without `start()`. Its ordinary unref'd timeout runs every 30 seconds, never overlaps a run, and claims at most three bindings per pass.

`WorkspaceExecutionService` keeps claim and settle commands private and exposes only the callbacks used by the reconciler. The SQLite bridge additively migrates `settled`, `last_polled_at`, and `lease_until` for existing binding tables. `BEGIN IMMEDIATE` serializes claims; the bridge returns only `{ projectId, jobId, clientId }`, orders eligible work by oldest `last_polled_at` then creation time and stable IDs, enforces a 30-second minimum poll interval, and assigns a 120-second lease. Settlement matches the complete project/job/client owner key.

Each claimed binding is synchronized through `AgentWorkspaceService.sync(projectId, jobId, clientId)`, which rechecks that client's current project membership and the stored execution owner. Settlement requires an explicit terminal `dispatch.state` (`complete`, `completed`, `failed`, or `cancelled`), `projectionPending === false`, and `resultsUnavailable === false`. Nonterminal, missing, ambiguous, unavailable-result, or pending-projection outcomes remain unsettled for a later lease. The reconciler never calls `job_submit`, invokes a model, changes ownership, or returns prompt/provider error text; its run result contains counts only.

Focused verification uses an isolated SQLite database and local Python CLI for schema migration, persistent lease behavior, owner-scoped settlement, and queue removal. Injected callbacks cover terminal gating, overlap, stop, and uncertain outcomes. This is ordinary backend reconciliation of existing bindings, not a paid-work scheduler or proof of production fanout.
