# Oracle apply controls

The Oracle model page now reads the optional `snooze.oracle_apply.OracleApplyController` status contract and renders process identity, heartbeat timestamp, loaded/requested revisions, active operation/error, readiness and recovery state. Process identity and heartbeat are shown separately; an alive PID identity is not presented as a fresh or healthy heartbeat. Missing coordinator support is represented as unavailable; it does not synthesize a healthy daemon or mutate maintenance state. The existing apply-readiness action remains preview-only.

Only an authenticated, same-origin, CSRF-verified `POST /admin/oracle/models` with the closed `apply-config` form (`revision`, `epoch`) invokes `controller.apply(expected_config_revision, expected_epoch)`. The backend checks current readiness and observed epoch before the call; the coordinator remains responsible for its durable reservation and atomic fence. After the action, the page snapshot is re-read so it shows current persisted operation, daemon and maintenance state. Successful POST uses neutral copy (“Apply request processed; inspect the current operation and daemon status below.”), not a completion claim. `reconcile_ready` labels the explicit action “Reconcile previous apply”; this path follows the coordinator without implying another restart. Historical complete operations do not block controls. GET and preview never pause/restart a service. Python IPC is bounded at 40 seconds for the coordinator's documented restart/poll window.

Verification uses fake bridge/controller state and temporary SQLite/config files. No live daemon restart or actual apply was attempted. On this base the coordinator module is not present, so production apply remains unavailable until the separately-owned coordinator/core API is integrated; the page fails closed meanwhile. `OA-UI` does not edit core or coordinator files.
