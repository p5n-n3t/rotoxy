# Oracle apply coordinator

This branch adds `snooze.oracle_apply.OracleApplyController` as the shared Python coordinator for the later admin route. Root integration should construct it with the trusted runtime fleet-config and queue-database paths, render `status()` on GET, and call `apply(expected_config_revision, expected_epoch)` only from the explicit authenticated Apply POST. It deliberately remains unmounted here. `status()` returns exactly `{daemon, operation, maintenance, ready, reason}` and reads the exact fleet-config revision plus the core's read-only daemon, apply-operation, and maintenance helpers. If any core helper is missing or the database schema is unsupported, readiness is false and status contains only safe unavailable values.

`apply(revision, epoch)` holds the fleet-config lock and an owner-only flock on the persistent `.apply.lock.v2` inode from compare-and-swap preflight through the core reservation, one fixed local service restart, daemon observation, and core completion. The lock inode is never unlinked, so process exit or crash releases the kernel lock without leaving an orphaned lock. A legacy `.apply.lock` sidecar is rejected for operator inspection. The current file revision is checked under the fleet lock and bound into the core reservation; the paused fence and old daemon may report an earlier revision because applying the new file is the purpose of this operation. The only production command is `/usr/bin/systemctl --user restart rotoxy-oracle-pool.service`, invoked with `shell=False`, a 10-second timeout, and only `HOME`, `XDG_RUNTIME_DIR`, and `DBUS_SESSION_BUS_ADDRESS` copied from the local server environment. No command, unit name, URL, or service arguments come from a request. A restart is accepted only after a different registered instance reports the reserved target config revision, same fence epoch, alive status, and heartbeat no more than 10 seconds old (with five seconds of future clock skew).

Any exception or missing post-restart proof keeps the maintenance fence and operation reservation in place. The coordinator records a bounded error code where possible and never retries an ambiguous restart. A later request with a prepared operation only completes it if the new daemon proof is present; a failed reservation may also be reconciled only when the exact new instance, target revision, fence epoch, and fresh heartbeat are now observed. Both paths call core completion without another restart. If proof is absent, failed operations remain blocked for audited recovery. A completed operation from an older fence epoch stays visible as history but does not block a later apply. There is no SQL cleanup or blind restart path.

Safe recovery is read-only first: inspect the coordinator status, core `read_config_apply_status`, `read_maintenance_status`, and `read_daemon_status`; compare the operation's target revision/epoch with the current config and daemon identity/heartbeat. If the operation is `prepared`, or `failed` with exact late daemon proof, a repeat coordinator request performs only the core completion step. Otherwise leave the fence paused, do not restart or delete/replay anything, and escalate for an audited core recovery procedure. The persistent v2 lock file may remain after a process exits; the kernel flock is released automatically. Do not remove or replace its inode while the coordinator may be running.

Focused tests inject the core contract and service runner with temporary private files. The base commit does not yet include daemon observation or durable apply-operation APIs, so this branch reports `core_api_unavailable` until the core integration lands. No live service, provider, or database was accessed.
