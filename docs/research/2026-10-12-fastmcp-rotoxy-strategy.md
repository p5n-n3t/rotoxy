# FastMCP and ROTOXY strategy (2026-10-12)

## Recommendation

Treat FastMCP as a possible Python MCP composition/adapter layer, not as a replacement for Token2OAuth’s working TypeScript OAuth gateway or its provider credential pool. Keep each system’s authority clear: Token2OAuth owns MCP-facing OAuth, encrypted upstream bearer credentials, account selection, and the existing bounded job APIs; Snooze owns the local job/recovery state; ROTOXY is the reported model API/federation layer, pending review of its local source. FastMCP does not provide a drop-in OpenAI-compatible inference gateway or the product-specific credit, account, project, and recovery contracts described here.

## Fit and migration sequence

Token2OAuth currently accepts MCP OAuth and proxies MCP calls; it also exposes scope-filtered local job, Oracle, and web tools (`src/server.ts`, `src/proxy.ts`). Its existing `OracleTools` facade validates arguments, binds the caller to a private queue namespace, and starts a bounded local Python command (`src/oracle-tools.ts`, `test/oracle-tools.test.mjs`). A second FastMCP listener for the same OraclePool would duplicate the auth and identity boundary without a demonstrated benefit. Snooze already has persistent job state and `RecoveryEngine`; `docs/implementation/2026-10-12-recovery-service.md` records monitor-service integration and a durable handoff path. That same checkpoint says the service has no cloud/headless/paid action adapter or resource-cap verifier. FastMCP may transport a future MCP task, but it will not fill that missing trusted action boundary by itself.

Proceed as a small, optional experiment only after the three core recovery steps in [the Swiss Army roadmap](../ROADMAP-SWISS-ARMY.md). First test one isolated FastMCP proxy behind Token2OAuth’s existing OAuth, with inbound auth-header forwarding off and explicit caller/project/account mapping. Verify both supported legacy initialize versions, OAuth scopes, base-path discovery/callbacks, request limits, restart behavior, and upstream error/usage handling. Compare latency and peak memory on the real host before packaging. Keep the current gateway as the only public issuer and rollback boundary. Adopt only a narrow component if this test demonstrates lower maintenance without changing ownership, policy, or stored credentials; otherwise keep the existing TypeScript proxy.

License/source work is pending for adoption: pin FastMCP and the resolved optional `[tasks]` dependency set (including Docket), audit dependency licenses/notices, check Python runtime compatibility, and review the exact release artifact. No package was installed or vendored in this review.

ROTOXY is not present in this cloud checkout. The assignment brief says its local README describes v2.1 model API rotation/routing, federated same-model pools, MCP HTTP/stdio registry, local CLI workers, and usage. These are **brief-supplied, not independently verified**. Before integrating, inspect the local repository’s version, code/tests, API/auth/storage contracts, licenses, and current deployment. If those capabilities are real, prefer one ROTOXY model/control plane connected to Token2OAuth’s existing MCP OAuth gateway over duplicating the model router. Preserve ROTOXY at `/` and Token2OAuth under its existing `/token2oauth` route; test both path-stripping and prefix-preserving proxy configurations.

The reported host is AWS Graviton, 2 vCPU/2 GB, on a tailnet. This is user-reported and supports only a **hypothesis** that lightweight gateway, scheduler, audit, and local CLI-control roles may fit. It is not a benchmark and does not establish local inference or large crawls as practical. Measure idle/peak RSS, CPU, storage, and queue lag on that host before adding FastMCP, Redis/Valkey, crawlers, or another worker.
